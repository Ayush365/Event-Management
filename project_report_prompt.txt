# PROJECT CONTEXT FOR CONTENT GENERATION
Here is the actual technical context based on the current codebase that you must use to write the report:

**System Architecture & Core Functionality:**
- A robust, full-stack Single Page Application (SPA) behavior-simulated responsive web application for managing event bookings.
- Segregated frontend (`client/`) and backend (`server/`) architecture.
- Role-Based Access Control (RBAC) with four distinct levels:
  - **Guest:** Unauthenticated users who can only browse available events.
  - **User:** Authenticated users who can register, login, and book event tickets securely.
  - **Organizer:** Special authenticated users who have an `organizer-dashboard.html` to create and manage events. Created events are 'Pending'.
  - **Admin:** System administrators who have an `admin.html` panel to approve/reject events, and oversee global users and all bookings.

**Database Schema Design (MySQL):**
- **Users Table:** `id`, `name`, `email`, `password` (bcrypt hashed), `role` (ENUM: Guest, User, Organizer, Admin).
- **Events Table:** `id`, `title`, `description`, `date`, `location`, `seats`, `organizer_id` (Foreign Key -> Users), `status` (Pending/Approved/Rejected).
- **Bookings Table:** `id`, `user_id` (Foreign Key -> Users), `event_id` (Foreign Key -> Events), `ticket_id`, `booking_time`. Features a regex check (`^TKT[0-9]+[0-9]+[A-Z0-9]+$`).

**Security & API Logic:**
- **Authentication:** JWT (`jsonwebtoken`) is used. Tokens are passed via HTTP Authorization headers from the Vanilla JS frontend fetch calls.
- **RESTful API Routes:** Handled via Express router modules (`auth.js`, `events.js`, `bookings.js`, `admin.js`).
- **Booking Concurrency:** Real-time backend seat availability checks against the `seats` column in the Events table before booking confirmation.
